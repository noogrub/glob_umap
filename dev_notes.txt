Our first desired matrix is:
  sample: clean_reciprocal
  split: train
  feature set: clean_observed
  columns, in order: u_g, g_r, r_i, i_z, z_y
  one row per astronomical object
  target label retained beside each row

WITH development AS (
    SELECT m.object_id,
           m.target_class,
           count(f.name) AS feature_count
    FROM ml.sample AS s
    JOIN ml.member AS m
      ON m.sample_id = s.sample_id
    JOIN ml.feature_set AS fs
      ON fs.sample_id = s.sample_id
    JOIN ml.feature AS f
      ON f.feature_set_id = fs.feature_set_id

Every target should have exactly 5 features. That was the point of our data preparation and filtering.

We need to construct the query that returns each object’s five values in a guaranteed order and convert that result to NumPy arrays.
The pathway for that is:
- ml.sample identifies clean_reciprocal
- ml.member identifies its objects, split, and target class.
- ml.feature_set identifies clean_observed.
- ml.feature stores each feature as one row: object, feature name, value, and uncertainty

Numerical code needs one object per row and one feature per column. Let's perform that reshaping while treating feature order as explicit data:

(.venv) jwb@elonius:~/Code/glob_umap$ psql -x -c "
WITH requested AS (
    SELECT item.name, item.position
    FROM unnest(
        ARRAY['u_g', 'g_r', 'r_i', 'i_z', 'z_y']::text[]
    ) WITH ORDINALITY AS item(name, position)
),
chosen AS (
    SELECT m.sample_id,
           m.object_id,
           m.target_class
    FROM ml.sample AS s
    JOIN ml.member AS m
      ON m.sample_id = s.sample_id
    WHERE s.name = 'clean_reciprocal'
      AND m.split = 'train'
    ORDER BY m.object_id
    LIMIT 3
)
SELECT chosen.object_id,
       chosen.target_class,
       array_agg(f.value ORDER BY requested.position) AS values
FROM chosen
JOIN ml.feature_set AS fs
  ON fs.sample_id = chosen.sample_id
JOIN ml.feature AS f
  ON f.feature_set_id = fs.feature_set_id
 AND f.object_id = chosen.object_id
JOIN requested
  ON requested.name = f.name
WHERE fs.name = 'clean_observed'
GROUP BY chosen.object_id, chosen.target_class
HAVING count(*) = (SELECT count(*) FROM requested)
ORDER BY chosen.object_id;"

Before we do that, let's adjust our appraoach to use catalog identities instead of our internal database "object_id" value. Catalog identities are immutable. A rebuilt database could theoretically assign different object IDs. The catalog identity remains tied to the documented, checksummed source.

(.venv) jwb@elonius:~/Code/glob_umap$ psql -c "
SELECT m.object_id,
       catalog.code AS origin_catalog,
       origin.source_key,
       m.target_class
FROM ml.sample AS s
JOIN ml.member AS m
  ON m.sample_id = s.sample_id
JOIN core.object AS o
  ON o.object_id = m.object_id
JOIN core.record AS origin
  ON origin.record_id = o.origin_record_id
JOIN core.catalog AS catalog
  ON catalog.catalog_id = origin.catalog_id
WHERE s.name = 'clean_reciprocal'
  AND m.split = 'train'
ORDER BY catalog.code,
         (origin.source_key::jsonb ->> 1)::bigint
LIMIT 5;"

source_key contains the source file and the row number in that checksummed file. The database column is text containing a JSON array. 
The expression "origin.source_key::jsonb ->> 1" means interpret the text as JSON; select array element 1—the second element; return it as text.
Then we do "(origin.source_key::jsonb ->> 1)::bigint" to convert that to integer, insuring that we get proper ordering instead of lexical "1, 10, 100, 11" kinds of results.

We're using psycopg3 to connect to Postgres.
